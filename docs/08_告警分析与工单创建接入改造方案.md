# 告警分析与工单创建接入改造方案

## 1. 目标

基于 [07_LangChain_Agent_告警分析到工单创建_集成开发指导.md](./07_LangChain_Agent_告警分析到工单创建_集成开发指导.md)，在当前 TypeScript Demo 上新增一条可演示的 Agent 主链路：

1. 查询当前告警列表
2. 选择并分析某条告警
3. Agent 发起“是否建单”的人机确认
4. 用户确认后创建工单
5. 返回结构化工单结果

本方案默认保持当前 Demo 的精简技术边界不变：

- 继续使用 TypeScript + Express + LangChain + `axios`
- 不引入数据库、消息队列或新的中间件平台
- 告警工作流状态仍按 `userId` 保存在内存中
- 不把告警链路接入定时任务系统

## 2. 需要接入的能力

### 2.1 最小必需能力

| 能力 | 建议 Tool 名 | 后端来源 | 说明 |
| --- | --- | --- | --- |
| 创建告警分析会话 | `create_alarm_session` | `POST /api/v1/new_session` | 为后续分析提供 `session_id` |
| 查询告警列表 | `list_alarms` | `GET /api/v1/alarms` | 返回可供 Agent 选择的候选告警 |
| 分析指定告警 | `analyze_alarm` | `POST /api/v1/process_alarms` | 后端为 SSE，Tool 层需聚合为结构化结果 |
| 创建工单 | `create_work_order` | Dify Workflow API | 需要告警对象、分析摘要和业务上下文 |

### 2.2 建议补齐的辅助能力

| 能力 | 建议 Tool 名 | 后端来源 | 说明 |
| --- | --- | --- | --- |
| 查询会话状态 | `get_alarm_session` | `GET /api/v1/session/{session_id}` | 长对话恢复、排障辅助 |
| 人工修正决策 | `override_alarm_decision` | `POST /api/v1/decision/override` | 不是主链路必需，但适合二次决策场景 |

### 2.3 不做成 Tool 的步骤

- “是否派单”不落成真实后端 Tool。
- 该步骤改为 Agent 的确认节点，写入 `pendingConfirmation=create_work_order`。
- 用户只有在明确回复“是/确认/建单”后，才允许进入 `create_work_order`。
- 当前仓库已有的开放式 `/api/v1/chat` 不作为主分析 Tool，主链路仍走 `process_alarms`。

| 当前文件 | 现状 | 改造方向 |
| --- | --- | --- |

## 4. 推荐改造设计

### 4.1 分层方式

建议把新增能力拆成 3 层，和 07 文档保持一致，但按当前仓库目录改造成 TypeScript 版本：

1. HTTP Client 层
   - `src/clients/alarm-agent-client.ts`
   - `src/clients/workorder-client.ts`
   - 职责：真实 HTTP 请求、超时、SSE 消费、原始响应保留、基础日志
2. Tool 封装层
   - `src/tools/alarm-tools.ts`
   - `src/tools/workorder-tools.ts`
   - 职责：参数校验、输入输出 schema、结构化结果、错误模型
3. Agent 编排层
   - `src/services/agent.ts`
   - 可选拆出 `src/services/agent-session-store.ts`
   - 职责：选择告警、维护状态、触发确认，并在建单前检查全局配置可用性

### 4.2 会话状态建议

当前 `Map<string, BaseMessage[]>` 只够保存聊天记录，不够承载业务工作流。建议升级为“按 `userId` 存储的会话对象”，至少包含：

| 字段 | 说明 |
| --- | --- |
| `messages` | 最近 3 轮对话消息 |
| `alarmSessionId` | 告警分析会话 ID |
| `alarmList` | 最近一次查询到的告警列表 |
| `selectedAlarm` | 当前选中的告警 |
| `lastAnalysisMarkdown` | 最近一次分析结果 |
| `pendingConfirmation` | 当前等待确认的动作，首轮固定为 `create_work_order` |
| `lastWorkOrderResult` | 最近一次建单结果 |

### 4.3 建单配置来源

`create_work_order` 依赖 `tenant_id`、`pmms_authorization` 和 Dify `user`。本轮统一收敛为“仅从全局配置读取”，不再设计运行时注入或按 `userId` 映射。

建议由 `src/config/index.ts` 统一解析以下配置项：

- `WORKORDER_TENANT_ID`
- `WORKORDER_PMMS_AUTHORIZATION`
- `WORKORDER_USER`
- `WORKORDER_WORKFLOW_URL`
- `WORKORDER_WORKFLOW_API_KEY`
- `WORKORDER_WORKFLOW_TIMEOUT_MS`
- `MOCK_CREATE_WORK_ORDER`

行为约束如下：

- `WORKORDER_TENANT_ID`、`WORKORDER_PMMS_AUTHORIZATION`、`WORKORDER_USER` 对建单功能都是必需项。
- 这 3 项缺任意一个时，应用仍可启动，但 `create_work_order` 必须返回 `missing_business_context`。
- `list_alarms` 与 `analyze_alarm` 不受影响，用户仍可完成告警查询与分析。
- `/chat` 继续只承载 `userId` 和 `message`，不追加 `context` 或业务身份字段。

### 4.4 SSE 与工单映射约束

- `list_alarms` 默认 `status` 传空字符串，表示不过滤处理状态；只有用户明确要求“未处理告警”时，Agent 才显式传 `Untreated`。
- `analyze_alarm` 不把原始 SSE 直接暴露给 Agent，只返回 `analysis_markdown`、`raw_events` 和辅助提示字段。
- `create_work_order` 不能直接吃整段长 Markdown，需先清洗成 100 到 400 字的 `fault_desc`。
- 建单前必须校验 `pendingConfirmation === create_work_order`。
- 缺少全局建单配置时，在 Tool 层直接阻断，不让 Agent 假装建单成功。

## 5. 建议新增配置

| 配置项 | 用途 |
| --- | --- |
| `ALARM_AGENT_BASE_URL` | 告警后端服务地址 |
| `ALARM_AGENT_TIMEOUT_MS` | 告警接口默认超时 |
| `WORKORDER_WORKFLOW_URL` | Dify Workflow 地址 |
| `WORKORDER_WORKFLOW_API_KEY` | Dify Workflow 鉴权令牌，如需 |
| `WORKORDER_WORKFLOW_TIMEOUT_MS` | 建单接口超时 |
| `MOCK_CREATE_WORK_ORDER` | Dify 不可达时的 Demo 兜底开关 |
| `WORKORDER_TENANT_ID` | 全局建单租户 ID |
| `WORKORDER_PMMS_AUTHORIZATION` | 全局建单业务令牌 |
| `WORKORDER_USER` | Dify 请求体中的全局 `user` 标识 |

## 6. 建议实施顺序

1. 先落告警域 HTTP Client 与 Tool 封装，打通 `create_alarm_session`、`list_alarms`、`analyze_alarm`。
2. 再扩展 Agent 会话状态、告警选择规则和确认节点。
3. 最后接 Dify 建单、`fault_desc` 清洗、mock/live 切换和结果回写。

对应 spec 拆分建议：

- `specs/25-alarm-integration-tools.spec.md`
- `specs/26-alarm-agent-workflow.spec.md`
- `specs/27-workorder-dispatch.spec.md`

## 7. 验收闭环

最小可演示闭环如下：

1. 用户输入“查看当前未处理告警”
2. Agent 调用 `list_alarms` 并返回编号列表
3. 用户输入“分析第 2 条告警”
4. Agent 自动补齐会话、调用 `analyze_alarm`、总结分析结论
5. Agent 追问“是否需要创建工单”
6. 用户输入“是，创建工单”
7. Agent 调用 `create_work_order`，返回工单编号、标题、等级、负责人和时间窗口

## 8. 已识别风险

- 全局建单配置缺失会导致建单能力不可用，但不应影响告警查询与分析链路。
- `process_alarms` 为 SSE，若事件格式不稳定，Tool 层需要支持部分结果回传。
- Dify Workflow 在 LangChain 运行环境里的直连性、鉴权方式和返回字段仍需要联调确认。
- 当前《需求规格说明书》尚未显式纳入告警与建单域，进入编码前应将本方案回写到正式需求基线或增量需求文档。
