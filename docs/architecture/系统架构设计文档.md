## 1. 架构目标

本阶段架构需要同时满足以下目标：

- 统一 Agent 入口处理 LINE 与 `/chat` 消息
- 通过 Tool Registry 承载任务管理与 Tavily 搜索能力
- 通过 Task Repository 管理运行时任务与 JSON 持久化
- 通过 Scheduler Service 调度“每日天气”任务并执行主动推送
- 保持 Demo 架构精简，不引入数据库、消息队列和复杂中间件

## 2. 技术基线

| 层级 | 技术选型 | 说明 |
|------|---------|------|
| Web 服务 | Express 4.x | 承载 Webhook、调试与管理接口 |
| LINE 接入 | `@line/bot-sdk` 9.x | 签名校验、Reply、Push |
| Agent | `langchain` 1.x | 使用官方 `createAgent()` |
| 模型提供商 | `@langchain/openai` 1.x | 接入 OpenAI-compatible 模型 |
| 搜索工具 | `@langchain/tavily` 1.x | 外部实时信息查询 |
| 调度 | `node-cron` 3.x | 每日天气任务调度 |
| HTTP 调用 | `axios` 1.x | 天气 API 调用 |
| 配置 | `dotenv` 16.x | 环境变量管理 |

## 3. 整体架构

### 3.1 主链路

```text
LINE User / POST /chat
        |
        v
Express Routes
  |- /webhook
  |- /chat
  |- /api/tasks
  |- /health
        |
        v
Agent Orchestrator
        |
        +--> Tool Registry
        |      |- task.create / list / update / delete
        |      |- search.tavily
        |
        +--> LLM Provider
        |
        +--> Short-term Memory (Map by userId)
        |
        v
Reply Builder / JSON Response

Task Repository
  |- in-memory task index
  |- src/config/tasks.json write-back
        |
        v
Scheduler Service
  |- load / reload tasks
  |- call Weather API
  |- push LINE message
```

### 3.2 模块关系

| 模块 | 核心职责 | 不负责 |
|------|---------|--------|
| `routes/webhook` | 接收 LINE 回调、校验签名、转交 Agent | 业务决策、任务 CRUD 细节 |
| `routes/chat` | 调试入口，模拟同一 Agent 链路 | 绕过 Agent 的直接调用 |
| `routes/tasks` | 最小任务管理与手动执行接口 | 用户自然语言解析 |
| `services/agent` | 统一消息编排与工具调用 | 直接读写 JSON 文件 |
| `tools/*` | 对外暴露标准化工具 | 路由层协议处理 |
| `services/task-repository` | 任务内存索引、所有权校验、JSON 持久化 | 天气 API 调用 |
| `services/scheduler` | 任务调度、天气拉取、主动推送 | 用户消息意图识别 |
| `services/line` | Reply/Push 封装 | Agent 决策 |

## 4. 核心模块设计

### 4.1 Agent Orchestrator

#### 职责

- 使用 `createAgent()` 创建统一 Agent 实例
- 接收 `userId` 与消息文本
- 注入短期上下文
- 根据用户意图决定直接回复、调用任务工具或 Tavily 搜索
- 输出最终文本回复和工具调用结果摘要

#### 设计约束

- `/webhook` 与 `/chat` 必须复用同一 Agent 服务入口。
- Agent 只能调用已注册工具，不能绕过 Tool Registry 直接访问底层服务。
- 对话上下文按 `userId` 管理，最多保留最近 3 轮消息。

### 4.2 Tool Registry

#### 职责

- 统一注册工具名称、输入、输出和错误语义
- 向 Agent 暴露标准化工具集合
- 约束首批工具范围，避免临时逻辑散落在路由或 Agent prompt 中

#### 首批工具

| 工具 | 描述 |
|------|------|
| `task.create` | 创建每日天气任务 |
| `task.list` | 列出当前用户任务 |
| `task.update` | 更新当前用户任务 |
| `task.delete` | 删除当前用户任务 |
| `search.tavily` | 查询实时外部信息 |

### 4.3 Task Repository

#### 职责

- 在内存中维护任务索引
- 从 `src/config/tasks.json` 加载任务
- 处理任务创建、查询、更新、删除
- 校验任务所有权
- 负责 JSON 持久化回写
- 在持久化成功后触发 Scheduler 刷新

#### 推荐数据结构

```text
Map<string, WeatherTaskRecord>
  key: taskId
  value:
    - id
    - type = daily_weather
    - ownerUserId
    - city
    - dailyTime
    - enabled
    - source
    - createdAt
    - updatedAt
```

### 4.4 Scheduler Service

#### 职责

- 启动时加载全部有效任务
- 把 `dailyTime` 转换为调度表达式
- 在任务 CRUD 后刷新注册状态
- 执行天气数据拉取、消息渲染和 LINE 推送
- 记录执行日志与失败原因

#### 调度刷新机制

1. Task Repository 成功写回 `src/config/tasks.json`
2. Repository 通知 Scheduler 触发 `reload()`
3. Scheduler 停止旧任务注册
4. Scheduler 重新注册全部 `enabled=true` 的有效任务
5. 刷新结果写入日志，供 `/health` 与 `/api/tasks` 查询

### 4.5 Tavily Search Tool

#### 职责

- 封装 Tavily 搜索调用
- 向 Agent 提供标准化搜索结果
- 统一处理搜索超时、配额错误和降级回复

#### 设计约束

- Tavily 仅用于实时外部信息查询。
- Tavily 结果不直接持久化。
- 搜索失败时返回可读错误，不暴露 API Key。

## 5. 关键流程

### 5.1 普通聊天流程

1. 用户发送普通问题到 LINE 或 `/chat`
2. 路由提取 `userId` 和文本
3. Agent 读取上下文并判断是否需要工具
4. 如果无需工具，直接生成回复
5. Webhook 通过 Reply API 返回；`/chat` 以 JSON 返回

### 5.2 自然语言创建任务流程

1. 用户发送“每天早上 8 点给我推送北京天气”
2. Agent 识别为任务创建意图
3. 若缺少城市或时间，Agent 先追问补全
4. Agent 调用 `task.create`
5. Task Repository 写入内存并持久化回 `src/config/tasks.json`
6. Scheduler 刷新注册状态
7. Agent 返回创建成功说明

### 5.3 Slash Command 任务流程

1. 用户发送 `/task update taskId=weather-001 time=09:00`
2. Agent 先按显式命令解析，走确定性分支
3. 调用对应任务工具
4. 校验当前用户是否拥有该任务
5. 成功后刷新调度器并返回结果

### 5.4 定时执行流程

1. Scheduler 到达任务执行时间
2. 根据任务中的城市参数调用天气 API
3. 渲染天气文本消息
4. 通过 `LineService.pushMessage()` 向 `ownerUserId` 推送
5. 记录执行结果

### 5.5 实时搜索流程

1. 用户询问实时信息
2. Agent 判断问题依赖外部搜索
3. Agent 调用 `search.tavily`
4. 工具返回摘要结果
5. Agent 整理文本并回复用户

## 6. 接口与路由职责

| 路由 | 角色 | 说明 |
|------|------|------|
| `POST /webhook` | 外部入口 | 只负责接收、签名校验、快速确认 |
| `POST /chat` | 调试入口 | 与 Webhook 走同一 Agent 逻辑 |
| `GET /api/tasks` | 管理接口 | 查询当前用户任务 |
| `POST /api/tasks` | 管理接口 | 直接创建任务，用于调试和回归 |
| `PATCH /api/tasks/:taskId` | 管理接口 | 直接更新任务 |
| `DELETE /api/tasks/:taskId` | 管理接口 | 直接删除任务 |
| `POST /api/tasks/:taskId/execute` | 管理接口 | 手动执行任务 |
| `GET /health` | 健康检查 | 暴露基础状态和调度器情况 |

## 7. 可观测性与错误处理

### 7.1 日志要求

- `logs/app.log`：应用启动、Webhook、Agent、Tavily、HTTP 错误
- `logs/scheduler.log`：调度器启动、停止、注册、执行结果
- 日志必须区分来源模块：`webhook`、`agent`、`task-repository`、`scheduler`、`tavily`

### 7.2 错误处理原则

- Webhook 必须尽快确认，业务失败不应导致 LINE 一直重试
- 单个任务执行失败不得影响其他任务
- JSON 持久化失败应作为任务 CRUD 失败处理
- LLM、Tavily、天气 API 失败时均返回可读降级信息

## 8. 部署与边界

### 8.1 单机 Demo 假设

- 单进程 Express 服务
- 单份 `src/config/tasks.json`
- 单机内存索引
- 无分布式锁、无任务抢占、无并发写冲突治理平台

### 8.2 非目标

- 不引入 PostgreSQL / Redis
- 不做多副本调度一致性
- 不实现复杂权限系统
- 不支持任意工具编排为定时任务
