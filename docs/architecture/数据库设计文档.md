## 1. 存储策略概述

### 1.1 Demo 阶段存储原则

| 数据类型 | 存储方式 | 说明 |
|---------|---------|------|
| Agent 对话上下文 | 内存 `Map<string, BaseMessage[]>` | 按 `userId` 保留最近 3 轮 |
| 任务索引 | 内存 `Map<string, AlarmFetchTaskRecord>` | 运行时 CRUD 使用 |
| 任务持久化 | `src/config/tasks.json` | 静态种子 + 运行时任务共存 |
| 执行记录 | 内存数组 | 仅保留最近若干次执行结果 |
| 配置与密钥 | 环境变量 | `.env` 文件 |

### 1.2 不使用数据库的原因

- Demo 优先验证主链路，不优先搭建正式持久化层
- 避免迁移、部署和运维成本
- 与单进程 `node-cron` 方案保持一致
- 便于在文档评审通过后再按 spec 决定是否升级存储方案

## 3. JSON 文件设计

### 3.1 文件路径

任务持久化文件统一为：

`src/config/tasks.json`

### 3.2 任务结构

```json
{
  "tasks": [
    {
      "id": "alarm-task-001",
      "type": "alarm_info_fetch",
      "name": "当前未处理告警定时获取",
      "ownerUserId": "U1234567890",
      "alertScope": "当前未处理告警",
      "cron": "0 0 8 * * *",
      "enabled": true,
      "source": "natural_language",
      "createdAt": "2026-03-18T08:00:00.000Z",
      "updatedAt": "2026-03-18T08:00:00.000Z"
    }
  ]
}
```

### 3.3 字段说明

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `id` | string | 是 | 任务唯一标识 |
| `type` | string | 是 | 固定为 `alarm_info_fetch` |
| `name` | string | 是 | 展示与日志使用 |
| `ownerUserId` | string | 是 | 当前用户 ID，也是推送目标 |
| `alertScope` | string | 是 | 告警查询范围 |
| `cron` | string | 是 | 6 字段 cron 表达式，例如 `0 0 8 * * *` |
| `enabled` | boolean | 是 | 是否启用 |
| `source` | string | 是 | `api_seed`、`natural_language`、`slash_command`、`api` 等 |
| `createdAt` | string | 是 | ISO 8601 时间 |
| `updatedAt` | string | 是 | ISO 8601 时间 |

### 3.4 设计取舍

- 不再把 `schedule`、`targets`、`template` 作为对用户暴露的主配置字段。
- 调度表达式直接持久化为 6 字段 `cron`，避免运行时二次推导和双重格式约束。
- 推送目标固定为 `ownerUserId`，不支持自定义 `targets`。
- 消息模板由系统内部固定，不暴露为用户可编辑字段。

## 4. 持久化与回写规则

### 4.1 启动加载

1. 读取 `src/config/tasks.json`
2. 反序列化为任务数组
3. 建立内存任务索引
4. 过滤无效或重复任务
5. 把有效任务交给 Scheduler 注册

### 4.2 写回流程

1. Agent 或管理接口发起任务 CRUD
2. Task Repository 在内存中生成变更结果
3. 校验所有权、字段格式与唯一性
4. 把完整任务集合写回 `src/config/tasks.json`
5. 写回成功后提交内存状态并触发 Scheduler 刷新
6. 写回失败时返回错误，不把失败状态视为最终成功

### 4.3 静态种子与运行时任务

- 静态种子任务与运行时任务共存于同一个 `tasks` 数组
- 通过 `source=api_seed` 区分项目预置任务
- 运行时创建任务可使用 `natural_language`、`slash_command` 或 `api`
- 服务重启后，不区分来源地重新加载全部有效任务

## 5. 调度数据流

### 5.1 任务 CRUD 到调度刷新

```text
User Message / API
      |
      v
Task Repository
      |
      +--> validate owner + fields
      |
      +--> update in-memory index
      |
      +--> write src/config/tasks.json
      |
      v
Scheduler.reload()
      |
      v
Active Cron Jobs
```

### 5.2 定时执行

```text
Cron Trigger
   |
   v
Scheduler Service
   |
   +--> resolve alertScope
   +--> call alarm service / alarm workflow
   +--> render fixed alarm summary message
   +--> LINE push to ownerUserId
   +--> record execution result
```

## 6. 未来扩展预留

### 6.1 可能迁移到正式存储

| 当前数据 | 未来候选存储 | 原因 |
|---------|-------------|------|
| 对话上下文 | Redis | 跨实例共享上下文 |
| 任务配置 | PostgreSQL | 避免 JSON 文件并发写问题 |
| 执行日志 | PostgreSQL / ClickHouse | 查询与审计能力增强 |

### 6.2 当前明确不做

- 数据库迁移脚本
- 任务分布式锁
- 多副本 JSON 同步
- 高并发写冲突治理
