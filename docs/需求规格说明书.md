## 1. 引言

### 1.1 编写目的

本文档描述 LINE Bot Demo 版本的正式需求基线，覆盖统一 Agent 消息处理、动态天气任务管理、Tavily 搜索工具接入以及定时天气推送能力。评审通过后，后续 `specs/*.spec.md` 将按本文件重新拆分和实现。

### 1.2 项目背景

本项目旨在快速构建一个可演示的 LINE Bot Demo，验证以下能力：

- LINE 平台消息收发与主动推送
- 基于 LangChain Agent 的统一消息处理
- 工具标准化封装与自动决策调用
- 通过自然语言或显式命令管理动态天气任务
- 定时天气推送与基础外部信息搜索

### 1.3 术语定义

| 术语 | 定义 |
|------|------|
| LINE Bot | 基于 LINE Messaging API 开发的聊天机器人 |
| Agent | 使用 LangChain `createAgent()` 构建的统一消息编排入口 |
| Tool | 供 Agent 调用的标准化能力单元，具有明确输入、输出和错误语义 |
| Tavily | 面向检索场景的搜索 API，本项目用于外部信息查询 |
| 动态任务 | 用户在运行时创建、更新、删除、查询的天气推送任务 |
| 静态种子任务 | 预置在 `src/config/tasks.json` 中、随项目一起发布的初始任务 |

## 2. 系统概述

### 2.1 系统目标

在 Demo 周期内完成一个可演示的 LINE Bot，实现：

- LINE 平台消息正常收发
- 统一 Agent 入口处理所有用户消息
- 自然语言与 `/task` 指令双轨任务管理
- 每日天气动态任务的 CRUD 与定时推送
- Tavily 搜索工具的自动决策调用
- `/chat` 与 LINE 消息链路行为一致

### 2.2 开发原则

| 原则 | 说明 |
|------|------|
| 核心优先 | 先保证聊天主链路、任务 CRUD、定时推送跑通 |
| 快速迭代 | 每次只推进一个可验证切片，先文档后实现 |
| 精简架构 | 不引入数据库、消息队列、复杂中间件平台 |
| 成熟框架 | 优先复用 LINE SDK、LangChain Agent、node-cron 等成熟能力 |
| 显式取舍 | 超出 Demo 范围的需求写入延期项，不隐含扩张 |

### 2.3 运行环境

| 环境要素 | 要求 |
|---------|------|
| 运行时 | Node.js 20+ |
| 网络 | 公网可访问，支持 HTTPS 或 ngrok |
| 外部服务 | LINE Messaging API、OpenAI-compatible LLM、Tavily Search API、天气 API |
| 编码 | 源码、JSON、配置、文档统一使用 UTF-8 |

## 3. 功能需求

### 3.1 LINE 消息交互与统一 Agent 入口

#### 3.1.1 功能描述

系统必须以统一 Agent 入口处理所有用户消息。`POST /webhook` 与 `POST /chat` 的消息语义保持一致，二者都先进入 Agent，再由 Agent 决定直接回复、调用工具还是发起追问。

#### 3.1.2 功能清单

| 功能编号 | 功能名称 | 功能描述 | 优先级 |
|---------|---------|---------|--------|
| F1.1 | Webhook 消息接收 | 接收 LINE 服务器推送的消息事件 | 高 |
| F1.2 | 签名校验 | 使用 `@line/bot-sdk` 中间件校验请求签名 | 高 |
| F1.3 | 统一 Agent 入口 | Webhook 与 `/chat` 共用一套 Agent 消息处理流程 | 高 |
| F1.4 | 文本消息回复 | 对文本消息生成回复并通过 Reply API 返回 | 高 |
| F1.5 | Slash Command 识别 | 识别 `/task create|update|delete|list` 命令 | 高 |
| F1.6 | 非文本消息跳过 | 非文本消息不进入业务处理，记录最小日志后跳过 | 中 |
| F1.7 | 异常降级 | Agent 或工具失败时返回可读的中文兜底回复 | 中 |

#### 3.1.3 处理规则

- LINE Webhook 仅负责接收、校验、快速确认 `{ "status": "ok" }`。
- 用户消息的业务理解必须在 Agent 层完成，Webhook 不能再直连单一 LLM `chat()` 调用。
- `/chat` 调试入口用于模拟同一 Agent 流程，避免调试路径与真实消息链路分叉。
- Slash Command 是自然语言之外的备用路径，语义必须确定且可回归测试。

### 3.2 Agent 与工具框架

#### 3.2.1 功能描述

系统必须采用 LangChain Agent 重构消息处理流程，提供统一的工具注册、输入输出约束、自动决策和失败降级能力。

#### 3.2.2 功能清单

| 功能编号 | 功能名称 | 功能描述 | 优先级 |
|---------|---------|---------|--------|
| F2.1 | Agent 创建 | 使用官方 `createAgent()` 创建统一 Agent | 高 |
| F2.2 | Tool Registry | 统一注册任务工具与搜索工具 | 高 |
| F2.3 | 工具输入输出约束 | 每个工具都定义明确的输入、输出和错误语义 | 高 |
| F2.4 | 自动工具决策 | Agent 根据用户意图决定是否调用工具 | 高 |
| F2.5 | 上下文记忆 | 按 `userId` 保留最近 3 轮对话上下文 | 中 |
| F2.6 | 错误降级 | LLM、工具、外部 API 失败时提供稳定降级回复 | 中 |

#### 3.2.3 首批工具范围

| 工具组 | 工具 | 用途 |
|------|------|------|
| 任务管理工具组 | `task.create` | 创建当前用户的每日天气任务 |
| 任务管理工具组 | `task.list` | 查询当前用户的任务列表 |
| 任务管理工具组 | `task.update` | 更新当前用户的任务 |
| 任务管理工具组 | `task.delete` | 删除当前用户的任务 |
| Tavily 搜索工具组 | `search.tavily` | 查询需要外部实时信息的问题 |

#### 3.2.4 工具边界

- Agent 可以自动决定是否调用 Tavily 搜索工具。
- Agent 可以自动决定是否调用任务管理工具。
- 天气定时任务的实际执行内容在本阶段固定为“每日天气推送”，不支持让用户把任意工具编排进定时任务。
- 本阶段不实现多工具工作流编排、长链式代理规划或跨用户协作。

### 3.3 动态任务管理

#### 3.3.1 功能描述

系统必须支持用户通过自然语言或显式 `/task` 命令，对“每日天气推送任务”进行动态创建、查询、更新和删除。

#### 3.3.2 任务模型约束

- 任务类型固定为 `daily_weather`。
- 任务归属固定为“当前用户管理当前用户自己的任务”。
- 推送目标固定为任务所属用户本人，不支持代他人创建或跨用户共享。
- 任务输入字段最小集合为：城市、每日执行时间、启用状态。
- 调度频率固定为“每天一次”，不支持工作日、每周、Cron 自定义等复杂周期。
- 时区固定使用服务器时区，不支持按任务单独指定时区。
- 任务创建来源需被记录，例如：`natural_language`、`slash_command`、`api_seed`。

#### 3.3.3 CRUD 功能清单

| 功能编号 | 功能名称 | 功能描述 | 优先级 |
|---------|---------|---------|--------|
| F3.1 | 自然语言创建任务 | 例如“每天早上 8 点给我推送北京天气” | 高 |
| F3.2 | 自然语言修改任务 | 例如“把天气提醒改成每天 9 点” | 高 |
| F3.3 | 自然语言删除任务 | 例如“删除我的北京天气提醒” | 中 |
| F3.4 | 自然语言查询任务 | 例如“我现在有哪些天气提醒” | 高 |
| F3.5 | 显式命令 CRUD | 支持 `/task create|update|delete|list` | 高 |
| F3.6 | 缺参追问 | 缺少城市或时间时，Agent 必须先追问再执行 | 高 |
| F3.7 | 所有权校验 | 任何更新或删除只能作用于当前用户自己的任务 | 高 |

#### 3.3.4 Slash Command 规范

| 命令 | 说明 | 示例 |
|------|------|------|
| `/task list` | 列出当前用户全部任务 | `/task list` |
| `/task create` | 创建任务，使用确定性参数 | `/task create city=北京 time=08:00 enabled=true` |
| `/task update` | 更新任务，必须带 `taskId` | `/task update taskId=weather-001 time=09:00` |
| `/task delete` | 删除任务，必须带 `taskId` | `/task delete taskId=weather-001` |

#### 3.3.5 持久化规则

- 启动时从 `src/config/tasks.json` 加载静态种子任务和历史运行时任务。
- 运行时任务管理以“内存索引生效 + JSON 文件持久化”为准。
- 创建、更新、删除成功后，必须把变更写回 `src/config/tasks.json`。
- 服务重启后，之前成功写回的任务必须可以重新加载。
- 静态种子任务与运行时任务共存于同一任务集合中，通过 `source` 字段区分来源。

### 3.4 天气定时推送执行

#### 3.4.1 功能描述

调度器负责把动态任务和静态种子任务统一注册为定时任务，按计划拉取天气数据并通过 LINE Push Message 主动推送给任务所属用户。

#### 3.4.2 功能清单

| 功能编号 | 功能名称 | 功能描述 | 优先级 |
|---------|---------|---------|--------|
| F4.1 | 任务加载 | 启动时加载有效任务 | 高 |
| F4.2 | 调度刷新 | CRUD 成功后刷新调度器注册状态 | 高 |
| F4.3 | 天气数据获取 | 通过天气 API 获取指定城市的天气信息 | 高 |
| F4.4 | 消息渲染 | 将天气数据渲染为文本消息 | 高 |
| F4.5 | 主动推送 | 使用 `pushMessage()` 向任务所属用户推送天气 | 高 |
| F4.6 | 手动执行 | 提供管理接口手动执行单个任务 | 中 |
| F4.7 | 执行日志 | 记录任务执行成功或失败 | 中 |

#### 3.4.3 执行约束

- 每个任务每天仅执行一次。
- 任务默认使用服务器时区解释 `dailyTime`。
- 单个任务执行失败不得影响其他任务继续运行。
- 任务执行结果需要可查询，便于 Demo 演示和排障。

### 3.5 Tavily 搜索工具

#### 3.5.1 功能描述

系统必须支持 Agent 对需要实时外部信息的问题自动调用 Tavily 搜索工具，并将结果整理后回复用户。

#### 3.5.2 功能清单

| 功能编号 | 功能名称 | 功能描述 | 优先级 |
|---------|---------|---------|--------|
| F5.1 | 搜索工具接入 | 接入 `@langchain/tavily` | 高 |
| F5.2 | Agent 自动决策 | 对实时信息类问题自动选择 Tavily | 高 |
| F5.3 | 搜索结果整合 | 输出简洁、可读的文本回复 | 中 |
| F5.4 | 搜索失败降级 | 搜索不可用时返回明确提示，不暴露密钥 | 中 |

## 4. 非功能需求

### 4.1 性能需求（Demo 版）

| 指标 | 要求 |
|------|------|
| Webhook 确认响应 | 尽快返回，避免 LINE 重投 |
| 普通消息完整回复时间 | 目标小于 10 秒 |
| 单任务执行超时 | 外部 API 必须设置超时 |
| 调试接口一致性 | `/chat` 与 LINE 消息链路行为一致 |

### 4.2 安全需求（Demo 版）

| 需求项 | 描述 |
|--------|------|
| Webhook 签名校验 | `POST /webhook` 必须使用 LINE 官方签名校验 |
| 密钥管理 | `LINE_CHANNEL_*`、`LLM_*`、`TAVILY_API_KEY`、天气 API 密钥统一走环境变量 |
| 日志脱敏 | 不在日志和响应中输出密钥、令牌或完整敏感配置 |
| 所有权约束 | 任务更新和删除必须限制为当前用户自己的任务 |

### 4.3 可维护性要求

- 源码、配置、JSON、文档统一使用 UTF-8。
- 工具必须是可扩展的标准化封装，避免业务逻辑散落在 Webhook 路由中。
- 任务 CRUD、调度执行、搜索调用必须有可读日志。

## 5. 接口需求

### 5.1 外部接口

| 接口 | 用途 | 说明 |
|------|------|------|
| LINE Webhook | 接收用户消息 | 使用 `middleware()` 校验签名 |
| LINE Reply Message | 回复用户消息 | Webhook 主链路使用 |
| LINE Push Message | 主动推送天气消息 | 调度器使用 |
| OpenAI-compatible LLM | Agent 推理与回复生成 | 通过 LangChain 调用 |
| Tavily Search API | 外部信息查询 | 由 Agent 自动决策调用 |
| 天气 API | 获取天气数据 | 由调度器执行任务时调用 |

### 5.2 内部接口

| 接口 | 用途 | 说明 |
|------|------|------|
| `POST /webhook` | LINE 回调入口 | 返回 `{ "status": "ok" }` |
| `POST /chat` | Agent 调试入口 | 请求体需包含 `userId` 与 `message` |
| `GET /api/tasks` | 列出当前用户任务 | 通过 `userId` 查询当前用户 |
| `POST /api/tasks` | 创建任务 | 面向调试和最小管理 |
| `PATCH /api/tasks/:taskId` | 更新任务 | 面向调试和最小管理 |
| `DELETE /api/tasks/:taskId` | 删除任务 | 面向调试和最小管理 |
| `POST /api/tasks/:taskId/execute` | 手动执行单个任务 | 便于演示 |
| `GET /health` | 健康检查 | 返回基础状态 |

### 5.3 内部接口返回规范

- 内部管理与调试接口统一返回 JSON。
- 推荐结构：

```json
{
  "code": "OK",
  "message": "ok",
  "data": {}
}
```

- 错误结构：

```json
{
  "code": "INVALID_ARGUMENT",
  "message": "time must use HH:mm format.",
  "errors": [
    {
      "field": "time",
      "message": "Expected HH:mm."
    }
  ]
}
```

## 6. 技术选型

### 6.1 技术栈（精简版）

| 层级 | 技术选型 | 版本 | 选型理由 |
|------|---------|------|---------|
| 运行时 | Node.js | 20+ | 满足 LangChain 官方运行时要求 |
| 语言 | TypeScript | 5.x | 类型安全 |
| Web 框架 | Express | 4.x | 轻量、可快速演示 |
| LINE SDK | `@line/bot-sdk` | 9.x | 官方支持签名校验与消息 API |
| Agent 框架 | `langchain` | 1.x | 使用官方 `createAgent()` 路径 |
| LLM Provider | `@langchain/openai` | 1.x | OpenAI-compatible 接口接入 |
| 搜索工具 | `@langchain/tavily` | 1.x | 使用官方推荐 Tavily 集成 |
| 调度 | `node-cron` | 3.x | 简单可靠的每日任务调度 |
| HTTP 客户端 | `axios` | 1.x | 调用天气 API |
| 配置管理 | `dotenv` | 16.x | 环境变量管理 |

### 6.2 依赖基线

- 本轮文档基线改为使用 `langchain` 的 Agent 能力，不再把“仅拆包直连 LLM”视为目标架构。
- `@langchain/openai` 继续负责模型提供商接入。
- Tavily 集成采用 `@langchain/tavily`，不使用已废弃的旧 community 集成。

## 9. 附录

### 9.1 环境配置

```bash
# 服务配置
PORT=3000

# LINE 配置
LINE_CHANNEL_SECRET=your-channel-secret
LINE_CHANNEL_ACCESS_TOKEN=your-access-token

# LLM 配置
LLM_API_KEY=your-llm-api-key

# 搜索与天气
TAVILY_API_KEY=your-tavily-api-key
```

### 9.2 非目标与延期项

- 不引入 PostgreSQL、Redis 或其他正式数据库

- 不把任意第三方工具开放为定时任务执行目标
- 不在本轮实现完整鉴权、审计、限流与性能专项优化
